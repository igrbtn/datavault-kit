# DataVault - архитектура

Статус: v0.9 (P0-P3 + guards + часть P4, см. roadmap). Разделы 9a-9g и 14a-14e - журнал решений по версиям. Имена tools без точек (`schema`, а не `vault.schema`): Claude Code показывает их как `mcp__datavault__schema`.

## 1. Зачем

Облачному агенту (Claude Code со скиллами) нужно работать с данными заказчиков: конфиги, выгрузки AD, логи, Excel, документы. Сами данные в контекст облачной модели попадать не должны.

DataVault - локальный слой между агентом и данными. Агент планирует и оркеструет. Данные читает и обрабатывает локальная LLM на той же машине. Агенту возвращаются только символы (handles), типизированные факты и агрегаты.

Паттерн: dual LLM / quarantined LLM. Привилегированная модель (Claude) не видит данных. Карантинная модель (локальная) видит данные, но не может вызывать tools и не управляет потоком.

## 2. Threat model

| Защищаем от | Как |
|---|---|
| Сырые данные в контексте и логах облачной модели | Агент получает только handles и типизированные ответы |
| Пересказ данных локальной моделью свободным текстом | Ответы только по JSON Schema, строковые поля проходят output guard |
| Prompt injection внутри данных ("игнорируй инструкции...") | Карантинная модель не вызывает tools, её выход - данные по схеме, а не инструкции |
| Деанонимизация через агрегаты | Минимальный размер группы (k), запрет запросов-дифференциалов |
| Обход vault (агент сам делает `cat` файла) | deny-правила Claude Code на пути vault + данные вне рабочих директорий сессии |
| Подбор handle по словарю | Handles - случайные ID, а не хэш значения |
| Случайная утечка в исходящий запрос | Второй рубеж - egress DLP-прокси (опционально, вне этого репо) |

Не защищаем от злонамеренного владельца машины и от компрометации самого Mac. Цель - не дать данным попасть в облако по ошибке или "попутно".

## 3. Инварианты

1. Ни один байт исходных данных не уходит агенту без прохождения output guard.
2. Каждый ответ vault - JSON по заранее объявленной схеме. Свободный текст из данных запрещён, кроме полей, явно помеченных `redacted_text` (после DLP и замены сущностей на handles).
3. Карантинная модель stateless по отношению к агенту: получает только (задача из фиксированного набора, кусок данных, схема), без произвольного промпта агента.
4. Реальные значения подставляются в результат только на локальной стороне (render/exec), и результат пишется в файл, который агент не читает.
5. Всё, что ушло агенту, пишется в audit log.

## 4. Схема

```
 Claude Code (cloud)          ---- MCP stdio ----            DataVault (local, this Mac)
 +------------------+                              +---------------------------------------+
 | plan, skills,    |  vault.search / extract /    |  Tool router + policy                 |
 | templates with   | ---------------------------> |    |                                  |
 | [[DV:PER:k3f9]]  |  aggregate / render / exec   |    v                                  |
 |                  | <--------------------------- |  Workers (task -> model route)        |
 +------------------+   handles + typed JSON       |    |  ner / extract / classify / embed |
        |                                          |    v                                  |
        v                                          |  Model gateway (OpenAI-compatible)    |
   egress DLP proxy (optional)                     |    LM Studio :1234  |  Ollama :11434  |
                                                   |    |                                  |
                                                   |  Handle store (SQLite, FileVault)     |
                                                   |  Index (bge-m3 vectors, local)        |
                                                   |  Output guard (DLP + schema + k-anon) |
                                                   |  Renderer / Executor                  |
                                                   |  Audit log                            |
                                                   +---------------------------------------+
                                                                  |
                                                     Cases: ~/DataVault/cases/<case>/
                                                     (raw data, never in agent cwd)
```

## 5. Ключевые понятия

**Case (дело).** Изолированное рабочее пространство: источник данных (папка, xlsx, БД, выгрузка) + политика + своя handle-таблица. Пример: `case-07`, `auto-20261105-1012`. Id дела виден агенту в каждом вызове, поэтому в нём не должно быть имени заказчика (`datavault case-rename`). Handles разных дел не пересекаются.

**Handle.** `[[DV:<TYPE>:<id>]]`, где `id` - 6 символов base32 из CSPRNG, уникальные в пределах дела. Типы: `PER`, `ORG`, `ACC` (учётка), `EMAIL`, `PHONE`, `HOST`, `IP`, `NET`, `DOM`, `AMT`, `DATE`, `DOC`, `SECRET`, `ID` (паспорт/ПИНФЛ и т.п.), `TXT` (фрагмент).
Одно значение в рамках дела всегда даёт один handle, поэтому агент видит связи ("один и тот же пользователь в двух группах"), но не значения.
Отличие от типового DLP-прокси: там токен часто - `sha256(detector:value)` без соли, его можно подобрать по словарю. Здесь - случайный ID с таблицей соответствий.

**Facets (разрешённые атрибуты).** Политика дела может выпускать обобщённые неидентифицирующие свойства handle: `HOST.role=DC`, `HOST.os=Windows Server 2019`, `ACC.enabled=false`, `ACC.last_logon_bucket=>180d`, `AMT.bucket=1-10M`. Это даёт агенту материал для рассуждений без значений.

## 6. MCP-контракт (tools)

| Tool | Вход от агента | Выход агенту |
|---|---|---|
| `vault.cases` | - | список дел, типы источников, размеры, политика (без содержимого) |
| `vault.schema` | case, source | структура: файлы, листы, колонки, типы, кол-во строк; имена колонок проходят guard |
| `vault.search` | case, запрос (с handles) | список `{doc: [[DV:DOC:..]], score, snippet_redacted}` |
| `vault.extract` | case, scope, имя схемы из каталога или JSON Schema | записи по схеме, все сущности заменены на handles |
| `vault.classify` | case, scope, набор меток | `{handle: label}` / счётчики по меткам |
| `vault.aggregate` | case, scope, group_by, metric | таблица агрегатов, группы меньше k подавлены |
| `vault.describe` | handle | разрешённые facets |
| `vault.compare` | handle_a, handle_b, поля | bool/diff по типам без значений |
| `vault.render` | case, шаблон (md/docx/drawio/yaml) с handles, out_path | `{path, sha256, unresolved: [...]}`; файл содержит реальные значения, агент его не читает |
| `vault.exec` | case, команда из allow-list с handles | код возврата + вывод, прогнанный через guard |
| `vault.audit` | case | что и когда ушло агенту (для отладки) |

Агент не передаёт карантинной модели произвольный промпт. Он выбирает задачу (`extract`/`classify`/...) и схему. Промпт собирает vault из шаблонов. Это главный барьер против того, чтобы агент (или инъекция) "уговорил" локальную модель выдать данные.

## 7. Конвейер обработки

```
источник -> parser (pdf/docx/xlsx/csv/txt/eml/cfg) -> chunks
        -> NER-проход (локальная LLM + regex-детекторы) -> сущности -> handle store
        -> индекс (bge-m3) по тексту с уже заменёнными сущностями
запрос агента -> router -> worker (задача + схема + chunks) -> локальная LLM (structured output)
        -> output guard -> агенту
```

Ингест делается один раз при создании дела. Индекс хранит pseudonymized-текст, так что даже `snippet_redacted` в поиске уже без значений.

### Output guard (последний фильтр перед агентом)

1. Валидация по JSON Schema: лишние поля отбрасываются, типы строгие, длина строк ограничена.
2. DLP-детекторы (`dlp/detectors.py`: секреты, карты/IBAN, UZ/RU PII, ПИНФЛ, телефоны, internal) - всё найденное заменяется на handle или блокирует ответ.
3. Сверка с handle store: если в строке встретилось любое известное значение дела (exact + нормализованное: регистр, транслит, пробелы), оно заменяется на handle. Это ловит то, что NER пропустил при ингесте, но знает таблица.
4. k-anonymity для агрегатов (по умолчанию k=5), запрет повторного запроса с отличием фильтра на одну запись.
5. Fail-closed: если guard упал или модель вернула невалидный JSON дважды, агент получает ошибку, а не сырой ответ.

## 8. Слой моделей

Обе среды дают OpenAI-compatible API, поэтому gateway один, провайдеры - конфиг.

| Runtime | Endpoint | Роль |
|---|---|---|
| LM Studio | `http://127.0.0.1:1234/v1` | основной: structured output через `response_format: json_schema`, MLX-модели, JIT-загрузка, TTL выгрузки |
| Ollama | `http://127.0.0.1:11434/v1` | вторичный: `format` с JSON Schema, gemma4/qwen2.5, embeddings |

Ollama: "Expose to the network" выключен (слушает `127.0.0.1`), "Cloud" выключить. Cloud-модели Ollama (`*-cloud`) работают через локальный `127.0.0.1:11434`, но инференс идёт на ollama.com, поэтому проверки loopback мало. Gateway (v0.1.1) отклоняет маршруты с `cloud` в имени при загрузке конфига, перед каждым запросом сверяется с `/api/tags` (`remote_host` - поймает переименованную через `ollama cp` облачную модель) и пишет warning в `models`. Context length в Ollama ставить 16k-32k: при 4k длинный промпт молча обрезается.

### Маршрутизация по задачам (стартовая)

Железо: M5 Pro, 24 GB unified memory. Одновременно держим одну "тяжёлую" модель или пару лёгких.

| Задача | Модель (основная) | Запасная | Почему |
|---|---|---|---|
| NER при ингесте (массово) | `qwen/qwen3-4b-2507` | `liquid/lfm2.5-1.2b` | много чанков, нужна скорость; regex страхует |
| extract по схеме | `liquid/lfm2-24b-a2b` (MoE, ~2B активных) | `qwen2.5:7b` | качество близко к крупной, скорость как у маленькой |
| classify | `qwen/qwen3-4b-2507` | `microsoft/phi-4` | короткий выход, enum |
| сложное извлечение, длинные документы, RU-юр.тексты | `qwen/qwen3.8-27b` | `gemma4:12b-mlx` | 16 GB, грузить по требованию, остальное выгружать |
| embeddings | `text-embedding-bge-m3` | `nomic-embed-text` | bge-m3 мультиязычный, RU/UZ лучше nomic |

`abliterated`/`uncensored`/`obliterated` варианты для vault не используем: у них хуже следование инструкциям и формату, а "отказов" в задачах извлечения и так нет.

Параметры по умолчанию: `temperature=0`, фиксированный `seed`, structured output обязателен, `max_tokens` по схеме. Модели для каждой задачи задаются в `config/models.yaml`, роутер умеет fallback при невалидном JSON.

Оценка качества моделей - отдельный eval-набор (`evals/`): размеченные документы с эталонными сущностями, метрики recall NER (главная - пропущенная сущность = утечка) и точность extract.

## 9. Render и exec

**Render** (`render.py`, tool `render`). Агент пишет шаблон с handles, vault подставляет значения (`Store.resolve`: самая полная форма - FQDN, полное ФИО, алиасы не берутся) и пишет файл в `cases/<case>/out/` (каталог 700, файлы 600). Экранирование по формату: YAML (если handle внутри `"..."` - JSON-escape), XML/drawio/html (entities), JSON, CSV. Форматы шаблона: `.md .txt .yaml .yml .csv .xml .drawio .json .html`; имя - `[a-z0-9._-]`, без путей. Агенту возвращаются только `bytes`, `sha256[:16]`, число подстановок и список `unresolved`.

**Exec** (tool `exec`). Allow-list в `tools.yaml` (пакет; override `~/DataVault/tools.yaml`): из коробки `docx` (pandoc), остальное (генераторы схем, конвертеры) добавляет владелец машины. Без shell, cwd = `out/`, минимальный env, timeout 300 с, вход - только файл из `out/` с разрешённым расширением. Агенту - exit code, список созданных файлов и хвост stdout/stderr через output guard. `out_files` - имена и размеры.

**Проверено на реальном деле (v0.4.0):** агент по выдаче `search` собрал отчёт (таблица компонентов, 17 handles) и YAML-спеку схемы (7 узлов, 6 handles); `render` -> `exec docx` -> `report.docx`, `exec` генератора схем -> png/svg/drawio. Генераторы схем в репо не входят, их подключают через `~/DataVault/tools.yaml`. Неизвестный handle остаётся как есть и виден в `unresolved`; `../x.yaml` и инструмент вне allow-list отклоняются. Ни один ответ инструментов не содержал значений.

## 9a. Prompt guard (v0.5.0)

Vault защищает данные дел, но промпт человека уходит в облако до любого инструмента. Хук Claude Code `UserPromptSubmit` запускает `datavault hook-prompt` локально до отправки: (1) известные значения всех дел заменяются на handles (sweeper, без словарных слов и алиасов); (2) regex DLP: `KEY=value` и `user:pass@host` в середине строки, затем правила ingest (DLP detectors + свои). SECRET/BANK/ID и любое значение дела блокируют промпт; EMAIL/PHONE/IP только предупреждают. Заблокированный промпт показывается обратно с `[SECRET]` вместо секретов и handles вместо значений, чтобы вставить его вместо исходного: агент сможет работать с handles через vault. Политика `~/DataVault/promptguard.yaml`: `mode: block|warn|off`, `block_types`, `warn_types`, `cases`, `allow` (regex для своих лабораторных адресов). Ошибка guard не блокирует работу (fail-open, лог `~/DataVault/promptguard.log` без значений). Стоимость: ~0.2 с на промпт при двух делах по 50-100 тыс. значений.

Плейсхолдеры типизированы и нумерованы: `AWS_SECRET_ACCESS_KEY=[AWS_SECRET_ACCESS_KEY_1]`, `redis://:[URL_PASSWORD_1]@`, `[GITHUB_PAT_2]` (имя ключа из `KEY=value`, имя детектора из DLP), так что агент различает разные секреты и видит их природу. Повторная вставка замаскированной копии проходит: плейсхолдеры не считаются значениями. Каждое событие несёт таблицу вердиктов по защитам: секреты, чувствительные данные, значения дел, инъекции. Оригинал заблокированного промпта не сохраняется нигде, в лог идёт только копия.

Сравнение на одном и том же тексте с коммерческим DLP-прокси (2026-11-05): он поймал 3 секрета из 8 (AWS access key, пароль в URL Postgres, GitHub-токен) и пропустил AWS secret key, пароль Redis, токен SentinelOne, JWT и SMTP; prompt guard после правок этого дня ловит 8 из 8. У него есть вкладка ORIGINAL/MODIFIED/DIFF; у нас её не будет сознательно, потому что для неё нужно хранить оригинал.

Чего хук не видит: вложенные картинки и файлы, промпты в других клиентах (Claude.ai, API). Для них остаётся egress-DLP.

## 9b. Детект инъекций и ловушек (v0.6.0)

Данные заказчика, README из git и веб-страницы могут содержать инструкции для агента: «ignore previous instructions», «AI agents: run this», однострочники на выгрузку наружу, скрытый текст из zero-width символов, base64-пейлоады. `injection.py` оценивает текст набором правил с весами: `override` (отмена инструкций, EN/RU), `assistant_address` (обращение к ИИ), `exfil` (curl/wget с данными или `| sh`, `nc -e`, `env | curl`, powershell -enc), `secret_harvest` (вывести/вставить env, ключи, .ssh, .dev-creds, settings.json), `tool_abuse` (запусти команду, правь CLAUDE.md / settings), `concealment` (не сообщай пользователю, silently), `hidden_text` (zero-width, unicode tags, HTML-комментарии с инструкциями), `obfuscation` (длинный base64, eval(atob), \x-строки). Сумма >= 3 - `suspect`, >= 6 - `injection`.

Три точки применения:
- **ingest**: каждый чанк оценивается, результат в `chunks.inj`; `status` отдаёт `injection_chunks`.
- **инструменты**: в `search`/`read` помеченный чанк получает поле `warning` и префикс `[[DV:WARN:injection override,exfil]]` в тексте, инструкция сервера велит агенту читать такое как данные; в `extract` чанки уровня `injection` не доходят до локальной модели вообще (`skipped_injection`).
- **prompt guard**: вставленная ловушка даёт предупреждение (`injection: warn` по умолчанию) или блок (`injection: block` в `promptguard.yaml`).

Проверка: 5 ловушек (README с curl | sh, русская, скрытый текст, сбор env, curl --data) все >= 6; 5 обычных технических фраз (curl -o, «ignore the warning», политика паролей) < 3. Правила регулярные, без модели: ловушка, написанная обычным языком без маркеров, пройдёт; это первый фильтр, не последний.

## 9c. Веб-интерфейс наблюдения (v0.7.0)

`datavault web` поднимает read-only страницу на `127.0.0.1:8787` (stdlib, без зависимостей): карточки дел (источники, чанки, handles, вызовы, чанки с инъекциями), лента событий по всем делам и prompt guard, детали вызова. Лог обращений `access` в хранилище дела теперь хранит и сам ответ инструмента (до 40 тыс. символов, ровно то, что получил агент) плюс счётчики handles, `[[REDACTED]]` и `[[DV:WARN]]`; prompt guard пишет события в `~/DataVault/promptguard.jsonl` с замаскированной копией промпта (оригинал не сохраняется). На странице handles, REDACTED и WARN подсвечены, так что видно, что ушло, что пришло, как замаскировалось и что заблокировалось. Значений дела в интерфейсе нет по построению: он читает только те же поля, что отдаются агенту.

## 9d. File guard: третья точка контроля (v0.7.0)

Vault работал только когда агент сам решал им воспользоваться: вложенный в чат xlsx он читал pandas'ом напрямую, и выгрузка целиком уходила в контекст. Хук `PreToolUse` на `Read|Bash` (`datavault hook-file`) смотрит на пути: файл данных (`xlsx xls xlsm csv tsv docx doc pdf eml msg`) вне разрешённых папок читать нельзя. Хук создаёт дело `auto-YYYYMMDD-HHMM` (id нейтральный, из имени файла ничего не берётся) с `source_dir` на папку файла и `include` на сам файл, запускает `ingest` в фоне и отклоняет вызов с объяснением: «файл в деле auto-..., ингест запущен, работай через status/schema/aggregate/rows/search/extract». Повторное обращение к тому же файлу находит существующее дело. Код агент читает как раньше; разрешённые папки и расширения в `promptguard.yaml` (`file_guard: {mode, extensions, allow}`), `~/DataVault` и фикстуры репо разрешены по умолчанию. Хук видит только пути, содержимое не читает; ошибки fail-open; событие пишется в `promptguard.jsonl`, его видно в UI.

Проверка: Read и `python -c "pd.read_csv(...)"` на csv вне разрешённых папок отклонены, дело создано, фоновый ингест 30 строк завершился за секунды (PER 30, ID 30). Попутно: таблица с голой колонкой `Name` рядом с SSN/картой/почтой/телефоном считается таблицей о людях (раньше имена из неё отбрасывались как не похожие на фамилии); GUID/SID такого эффекта не дают.

Детектор инъекций на реальных делах после переингеста: 0 помеченных чанков из 960 (документы) и 8916 (AD-выгрузка), то есть ложных срабатываний на настоящих данных нет.

## 9e. Режимы сессии: default и strict (v0.8.0)

Запретить агенту читать папку с документами заказчиков целиком нельзя: в сессиях внутри неё он по определению читает и правит документы. Поэтому два режима, выбор за человеком:
- **default** (всегда): prompt guard на секреты, значения дел и инъекции; file guard на файлы данных (xlsx, csv, docx, pdf, eml) вне разрешённых папок.
- **strict**: команда `/vault on [путь ...]` в промпте. Prompt guard запоминает режим для этой сессии (`~/DataVault/sessions/<session_id>.json`, корни = cwd + `DATAVAULT_STRICT_ROOTS` + указанные пути) и подкладывает модели контекст: «все документы под корнями - данные заказчика, работай через datavault». File guard в strict отклоняет любое чтение под корнями, кроме кода и конфигов (`.py .ps1 .sh .yaml .json ...`): markdown, txt, выгрузки, всё остальное идёт в дело. Одно дело на папку: первый файл создаёт `auto-...` с `source_dir` на папку, следующие добавляются в `include`, ингест перезапускается (handles сохраняются). `/vault off` возвращает default, `/vault status` показывает режим, `/vault bypass` переводит сессию в обход: guards только предупреждают, файлы читаются напрямую, ничего не маскируется (для данных, которые человек сам решил отдать в облако). Постоянный обход: `~/DataVault/promptguard.yaml` - `mode: warn|off`, `file_guard: {mode: warn|off, allow: [regex]}`. Команда не доходит до модели как задача: хук отвечает сообщением и контекстом.

Проверка: `/vault on` в cwd `docs/` -> Read `ARCHITECTURE.md` отклонён, дело создано; `/vault off` -> тот же Read проходит.

## 9g. P4 hardening (v0.9.0)

Vault стал единственным местом, где лежат данные заказчиков, значит он и есть главная цель. Что сделано:
- **`person_rows: deny`** в политике дела: по таблицам о людях `rows` отдаёт только неидентифицирующие колонки (`dropped_columns` в ответе), `read` по такой таблице отказывает и отправляет к `rows`/`aggregate`. Закрывает дыру «k-анонимность в агрегатах, но строки читаются по одной». По умолчанию `handles` (прежнее поведение), включается `datavault case-policy <case> person_rows deny`.
- **`extract_free_fields`** (по умолчанию 4): больше свободных строковых полей за вызов нельзя, остальное через enum, числа и булевы. Канал «по биту за запрос» остаётся, но каждый бит стоит вызова, и вызов виден в ленте.
- **`suppressed`** в `aggregate` стало булевым: точный размер подавленной группы был побочным каналом, которым B2 пользовался.
- **`datavault harden`**: отчёт о хосте - режим `~/DataVault` и файлы с лишними правами, FileVault, зарегистрированы ли оба хука, объём логов LM Studio. `--tighten` ставит 700/600, `--clean-lmstudio-logs` удаляет логи сервера LM Studio (в них сырые промпты NER и extract). Первый отчёт на машине автора: FileVault on, хуки on, 20 путей с 755/644 (исправлено), логи LM Studio 115 MB.
- **Шифрование SQLite не делается осознанно:** sweeper ищет значения в тексте и для этого нуждается в них в открытом виде на каждом вызове. Защита покоя - FileVault (диск) плюс права 700/600; `harden` проверяет оба условия.

Не сделано: red-team с инъекциями в данных на реальных делах (детектор есть, атакующих прогонов нет); eval-регрессия моделей при смене версии LM Studio; отдельный инструмент `verify` (локальная модель сверяет файл из `out/` с делом) - следующий шаг, потому что сравнение отчёта с исходником через облачного агента невозможно по построению.

## 13. Ограничения

- Recall NER - потолок защиты. Пропущенная при ингесте сущность может уйти в `redacted_text`. Смягчение: guard-сверка с таблицей, regex, и запрет свободного текста по умолчанию.
- Агрегаты и facets раскрывают информацию по совокупности. k-anon и политика facets - компромисс, не гарантия.
- Квазиидентификаторы (редкая должность + отдел) не ловятся regex. Нужны правила обобщения в политике дела.
- Качество рассуждений агента падает, когда он не видит значений (например, анализ опечаток в именах). Такие задачи делаются целиком локально (`vault.compare`, `classify`).
- 24 GB RAM: 27B-модель плюс индекс плюс всё остальное - на грани. Тяжёлую модель грузим по требованию.

Что изменилось по ходу:
- **Проверки правдоподобия по типу** (`store.plausible`): хост - с цифрой/дефисом/точкой, ФИО - с токеном формы фамилии, иначе решает gate по корпусу (слово не встречается со строчной буквы), логин от LLM - с `._$\@-`/цифрой или строчный, сумма - валюта или от 5 цифр, ключи конфигов и пути - не секреты. Перетипизация и повышение алиаса тоже проходят проверку.
- **Доверие по заголовку** только для структурных типов (SECRET/ACC/EMAIL/PHONE/ID/BANK); буквенные значения таких колонок, встречающиеся во многих документах (продукты), отбрасываются.
- **always_mask** в политике дела (`datavault case-mask`): название заказчика и домены, плюс автоматический вариант `DC=..,DC=..`; sweep матчит домен внутри FQDN.
- **Детекция**: `password ciphertext|cipher|N <value>`, MAC, подсети/диапазоны/шаблоны IP; NER свободного текста табличных колонок (Description, Примечание) даже без полного NER.
- **Инструменты**: `rows`; `aggregate` с `where`, двумя колонками, OU из DN, `count_true`, итогом без группировки; фильтр идентифицирующих колонок только по handle (сырое значение - ошибка, против вытягивания по битам); k-анонимность только для таблиц о людях; `schema source=all`; поиск по handle и точной фразе.
- **Скорость**: таблицы не эмбеддятся (ADRecon: 40 мин -> 84 с), связывание ФИО через индекс (было O(n^2)), sweep словарём вместо regex-альтернации.
- **Диагностика**: `datavault diag` (срабатывания правил с формой значений, без значений), `leakcheck` (сколько значений дела в тексте ответа).

Синтетика после всех правок: recall hard 1.0 / 0.997 / 1.0 (seed 7/11/23), без регрессий.

После раунда 4: gate имён учитывает частоту по документам (продукты и города), буквенные логины из колонок с LLM-типом - тоже; заполнители `____` и короткие числа не сущности; короткое имя хоста и FQDN - один handle; коды заказчика добавлены в always_mask.

**k-анонимность - косметика при наличии `rows`/`read`:** по таблице о людях агент видит строки по одной (с handles), поэтому подавление малых групп в `aggregate` защищает только от случайного взгляда. Настоящая защита потребует политики `person_rows: deny` (rows/read по таблицам о людях только для неидентифицирующих колонок) - не сделано.

Известные ограничения: `extract` со свободными полями остаётся каналом вытягивания по битам; LM Studio пишет промпты (сырые куски при NER/extract) в `~/.lmstudio/server-logs`; ADRecon CSV с кириллицей в cp1252 приходит как "???" (проблема выгрузки).

Вывод: по цифрам B равен A, по выводам беднее там, где нужны имена (классификация учёток, join по названиям GPO) или значения IP. Для аудита "что не так в домене" этого достаточно; для "кто именно" нужен render.

Исправлено по итогам (v0.4.1): NetBIOS -> HOST (и короткие имена из колонок-хостов); таблицы Category | Value (ADRecon Domain/Forest/About) типизируются построчно по категории, а не колонкой; `DisplayName`/`Name` считается именем человека только в таблицах о людях (есть SamAccountName/UPN/Title/Department/...), иначе GPO/группы/OU становились PER с алиасами "Policy", "Domain"; колонки, угаданные LLM как ACC/PER, но заполненные словарными словами (OU "Computers", "Printers"), не сущности (`/usr/share/dict/words`); логины вида `it_service`/`svc_*` внутри Description -> ACC. После `ingest --fresh` leakcheck отчёта B: 12 -> 2 известных значений (NetBIOS, который теперь маскируется, и одно словарное слово). Функциональные уровни и LAPS/PAM стали видны агенту.

**B2: повтор через vault после правок (0.4.1).** 6 мин, 93 вызова (aggregate 62, rows 19, schema 12), все 10 разделов; появились функциональные уровни, LAPS/PAM, деление админов на сервисные/персональные (по описаниям и типу handle), 199 устаревших ОС как у A. В контексте агента: 63 тыс. символов, 134 handles, 0 имён/хостов/IP/ID. Leakcheck отчёта: 0 реальных значений (3 словарных слова). Найденный побочный канал: агент сшивал GroupMembers с Users по SID, а SID не маскировался - в контекст ушло 57 уникальных SID (домен + RID). Исправлено: колонки SID/GUID -> ID-handles, join по handle работает так же.

## 14b. Prior art и риски (обзор 2026-11-04)

DataVault - вариант dual LLM / quarantined LLM (Willison 2023; CaMeL, DeepMind, arXiv 2503.18813). Близкие инструменты: Presidio (+ Deanonymizer), LLM Guard (Anonymize/Deanonymize + Vault, на уровне промпта, без корпуса), Private AI / Protecto / Tonic Textual (коммерческие, консистентные токены), LiteLLM PII guardrail (`output_parse_pii`). Облачные DLP (Nightfall, Lakera, Cloudflare AI Gateway) не подходят под модель угроз. Ближе всего к нашему ingest - Casper (2408.07004). Протокол локальная+облачная модель - MinionS (Stanford, 2502.15964): ~98% качества облака при 18% стоимости, но только при атомарной декомпозиции на чанки.

Риски, которые инвариант "только слова корпуса" НЕ закрывает:
1. **Covert channel через extract/aggregate.** Агент сам задаёт поля и enum: "фамилия начинается на А? yes/no", "длина имени". Ответ состоит из слов корпуса и проходит guard; так можно вытащить значение по битам. Нужно: запрет полей-предикатов над значениями сущностей (буквы, длина, сравнение с литералом), локальная классификация инструкции до исполнения, квоты и журнал.
2. **Quasi-identifiers** (Staab et al., ICLR 2024; Lermen 2026): должность + отдел + город + дата найма указывают на человека при псевдонимизированном ФИО. Нужно: генерализация (дата -> год, город -> регион), k-anonymity не только в aggregate, но и в read/search по таблицам с персонами.
3. **Differencing-атаки на aggregate:** пересекающиеся фильтры обходят k-порог. Нужен учёт истории запросов или бюджет.

Что взять:
- Natasha/Slovnet + pymorphy3: второй NER для RU-имён и генерация всех падежных форм вместо эвристических стемов; union с LLM NER повышает recall.
- MinionS-протокол для extract: атомарные вопросы на чанк, абстенция, ссылка на чанк, многораундовость.
- CaMeL-style capability-теги на handles (источник, клиент, чувствительность, кому можно ре-идентифицировать) + политика при ре-идентификации отчёта; соль handles per-case (уже: случайные ID per-case).
- Eval: presidio-research evaluator, TAB (direct + quasi identifiers), локальный LLM-атакующий, который пытается ре-идентифицировать псевдо-корпус (Yang/Gurevych 2407.11770).
